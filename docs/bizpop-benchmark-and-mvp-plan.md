# 애즈폼 구축 계획

2026년 11월 10일 · Bizpop 벤치마크 및 1차 출시 범위

## 1. 서비스 방향

**애즈폼(Adsform)**은 광고주가 캠페인을 주문하고, 참여자가 오퍼월에서 미션을 수행하면, 검증된 결과를 기준으로 집행 내역과 보상을 처리하는 서비스다. 첫 출시에서 증명할 흐름은 **광고주 주문 1건 → 참여자 미션 완료 1건 → 보상 1회 → 광고주 리포트 반영 1건**이다.

첫 고객은 소상공인과 중소 브랜드로 가정한다. 초기 상품은 애즈폼에서 직접 결과를 확인할 수 있는 **브랜드 퀴즈**와 **설문 응답** 두 가지로 제안한다. 참여자는 모바일 웹에서 모집하고, 검증된 참여에 대해 한 가지 모바일 쿠폰을 제공하는 방식으로 비공개 파일럿을 진행한다. 첫 고객군, 상품, 보상 방식은 현재 단계의 기획 가정이다.

## 3. 초기 공급 방식

| 방식 | 출시 조건 | 판단 |
|---|---|---|
| 애즈폼 자체 오퍼월 | 자체 모집 채널, 애즈폼에서 판정 가능한 미션, 쿠폰 지급 경로 | **초기안.** 주문과 보상 전 과정을 직접 검증할 수 있다. 수용량은 파일럿 참여자 모집 결과에 맞춘다. |
| 외부 오퍼월·매체 제휴 | 계약, 허용 미션, 공급 단가, 완료·취소 이벤트, 정산 내역 확인 | 제휴가 확보되면 추가한다. 기존 주문·캠페인 구조에 공급처와 외부 이벤트 식별자를 연결한다. |

| 사용자 | 1차 화면 | 주요 동작 |
|---|---|---|
| 공개 방문자 | 홈, 광고 상품·이용 안내, 오퍼월 입구, 도움말 | 광고 주문과 미션 참여로 각각 진입한다. |
| 광고주 | 대시보드, 캠페인 주문, 주문 목록·상세, 결제·예산 내역 | 상품 선택 → 미션 내용·목표 건수·일정 작성 → 견적 확인 → 제출 → 승인·집행·결과 확인 |
| 참여자 | 모바일 오퍼월, 미션 상세, 참여 내역, 보상 내역 | 자격·소요 시간·보상 확인 → 시작 → 응답 제출 → 결과와 사유 확인 → 보상 수령 |
| 운영자 | 주문 검수, 캠페인 운영, 제출 검토, 지급·정산 예외 | 승인·수정 요청·반려, 게시·일시중지, 참여 재검토, 쿠폰 지급 재처리, 미집행 예산 정리 |

### 광고 주문서

1. **상품 선택** — 미션 유형, 인정 기준, 건당 단가, 수량 제한과 소요 시간을 확인한다.
2. **내용과 일정** — 캠페인명, 브랜드, 질문 또는 퀴즈, 안내 문구, 대상 조건, 목표 수량, 일일 한도, 시작·종료일을 입력한다.
3. **견적 확인** — 확정 단가 × 목표 건수, 세금 표시, 결제 필요액, 이미 확보한 예산, 취소·부분 집행 정책을 한 화면에서 확인한다.
4. **제출·검수** — 주문 번호를 발급한다. 수정 요청을 받으면 사유와 대상 필드를 확인하고 재제출한다. 출시 후 미션의 보상 금액이나 검증 조건 변경이 필요하면 운영자가 새 버전의 적용 범위를 결정한다.

### 참여자 오퍼월

목록 카드에 **보상, 예상 소요 시간, 완료 조건, 마감**을 먼저 배치한다. 참여를 시작하면 짧은 시간 동안 자리를 예약하고, 제한 시간 안에 결과를 제출하도록 한다. 브랜드 퀴즈는 서버에서 조건을 판정한다. 설문은 필수 문항, 동일 미션 중복 여부, 미션별 자격을 검증하고 이상 건을 검수 큐로 보낸다. 참여 내역에는 심사 중, 승인, 반려 사유를 보여주고, 보상 내역에는 지급 대기, 지급 완료, 재처리 중을 구분한다.

### 운영자 화면

주문 검수 화면에서 광고주 요청 내용과 참가자에게 보일 내용을 함께 미리 본다. 캠페인 운영 화면에서는 모집 중인 자리, 심사 대기, 승인·반려, 지급 실패와 남은 예산을 확인한다. 승인·반려·중지·예산 조정에는 사유를 남기고, 정산 예외는 일반 운영 권한과 분리한다.

## 5. 집행·정산 규칙

| 구분 | 1차 규칙 |
|---|---|
| 주문 상태 | 작성 중 → 심사 중 → 승인. 심사 중에는 수정 요청 또는 반려가 가능하다. 수정 요청을 받은 광고주는 내용을 고쳐 재제출한다. |
| 캠페인 상태 | 게시 대기 → 진행 중 → 종료. 진행 중에는 일시중지·재개할 수 있다. 종료 사유는 목표 달성, 기간 만료, 운영 중지로 구분한다. |
| 참여와 지급 | 참여 상태는 시작 → 제출 → 승인 또는 반려이며, 미제출 참여는 만료된다. 지급은 대기 → 완료 또는 실패로 추적한다. 재시도는 같은 지급 건에 기록한다. |
| 수량과 예산 | 일일·전체 승인 한도에서 유효 예약, 심사 중 제출, 이미 승인된 건을 합산해 슬롯을 배정한다. 예약 만료나 반려로 반환된 자리는 기간과 예산 내에서 다시 연다. |
| 요금 | 주문에 상품 버전, 단가, 검증 조건, 세금 표시, 취소 정책을 저장한다. 파일럿에서는 승인된 참여 건수에 따라 집행액을 계산하고 미집행 예산은 종료 시 해제한다. 이미 들어온 제출 건의 검수를 마친 뒤 종료 정산을 확정한다. |
| 광고주 결제 | 비공개 파일럿은 계약·청구 기준으로 운영자가 입금 확인 후 예산을 승인한다. 공개 출시에서 직접 결제가 필요하면 PG 샌드박스에서 승인·취소·재전송을 검증한 뒤 붙인다. 충전형 포인트 운영은 별도 출시 결정이다. |
| 참여 보상 | 참가자의 현금 출금·송금 기능은 1차 범위 밖이다. 쿠폰 지급 요청에 고유 키를 부여하고, 응답을 잃었을 경우 같은 요청의 처리 결과를 대조한 뒤 재처리한다. |
| 수익 기준 | 캠페인 기여이익은 세금 제외 광고 매출에서 참여 보상 원가, 공급처 원가, 결제·지급 수수료, 건별 운영비를 차감해 본다. 광고주 단가는 Bizpop 단가와 독립적으로 결정한다. |

**핵심 지표 정의** — 광고주 화면의 진행률은 승인 완료 건수 ÷ 목표 건수로 표시한다. 심사 중 제출과 지급 실패는 별도 지표로 보여준다. 운영자는 집행 소진률, 제출→승인율, 지급 성공률, 건당 원가, 검수 대기 시간을 함께 확인한다.

## 6. 데이터와 구현 경계

- **핵심 데이터** — 사용자·광고주 조직, 상품·버전, 주문·견적, 캠페인, 참여 예약·제출, 집행 예산 거래, 보상 지급 거래, 운영 감사 이력.
- **서버 검증** — 견적은 서버에서 다시 계산한다. 주문의 수량과 옵션이 바뀌면 견적을 새로 확인시킨다. 남은 자리를 배정하는 순간과 승인 건수·예산을 반영하는 순간은 각각 데이터베이스 트랜잭션으로 처리한다.
- **중복 방지** — 캠페인과 참가자 조합에 기본적으로 1회 승인만 허용한다. 참여 승인 시 집행액과 지급 대기 건을 함께 기록한다. PG·쿠폰·외부 매체 이벤트는 공급처와 거래 식별자로 중복을 차단한다.
- **권한과 개인정보** — 광고주는 자기 조직 주문만 조회한다. 참여자 식별 정보와 쿠폰 전달 정보는 지급에 필요한 범위에서 수집하고 광고주 결과에는 집계 정보 또는 익명화한 응답만 제공한다. 운영 접근·내역 조정은 역할별로 제한하고 기록한다. [개인정보 보호법 제16조](https://www.law.go.kr/법령/개인정보보호법/제16조)
- **구현 제안** — 반응형 웹 앱과 PostgreSQL을 중심으로 광고주·참여자·운영자 화면을 구성한다. 예약 만료, 캠페인 시작·종료, 쿠폰 지급 및 대사는 재시도 가능한 백그라운드 작업으로 분리한다. 앱 배포와 외부 매체 API는 필요한 시점에 추가한다.

## 7. 구축 순서와 검증 기준

| 순서 | 산출물 | 통과 기준 |
|---|---|---|
| 1. 정책·와이어프레임 | 홈, 주문서, 주문 상세, 오퍼월, 미션 상세, 운영 검수 화면과 상태 규칙 | 운영자가 수량 제한, 검증, 미집행 처리, 보상 실패 시 조치를 화면 흐름에서 설명할 수 있다. |
| 2. 광고주 주문과 운영 검수 | 로그인·권한, 상품별 폼, 견적, 주문 목록·상세, 승인·수정 요청, 파일럿 예산 배정 | 수정 후 재제출 및 승인·게시가 된다. 같은 주문을 여러 번 제출해도 주문·예산 반영은 1회다. 타 광고주 주문은 조회할 수 없다. |
| 3. 모바일 오퍼월 | 목록·상세, 슬롯 예약, 퀴즈·설문 제출, 심사와 결과 반영 | 두 사람이 마지막 자리에 동시에 접근해도 한도 내에서 배정된다. 중복 제출·기한 경과·중지 후 신규 참여가 처리되고 승인 건수만 리포트에 반영된다. |
| 4. 보상·대사·파일럿 | 쿠폰 지급, 실패 처리, 잔여 예산 해제, 캠페인 리포트 | 지급 실패·타임아웃을 재처리해도 중복 지급이 없다. 미집행 잔액이 정확하고, 광고주 리포트·승인 이력·쿠폰 지급 기록이 서로 맞는다. |
| 5. 공개 출시 확장 | 결제, 알림, 확정된 공급처 연동 | 검증된 미션 수요와 운영 원가를 기준으로 공개 범위를 결정한다. 대행사 하위 계정, 대량 등록, 패키지는 반복 발주 수요에 따라 추가한다. |
